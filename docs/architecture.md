# Architecture

This document explains how the codebase is structured and why. Read it before you add a new package or a new kind of game system.

## Goals

1. **Multiplayer from day one.** Every gameplay rule must be able to run on the server.
2. **Clear separation.** Rendering, game logic, UI, networking and game data live in separate places.
3. **Data-driven content.** Races, buildings, units, upgrades and spells are defined as data, not hard-coded in logic.
4. **Small, working increments.** Add an abstraction when a second real use appears, not before.

## Packages

| Package          | Runs in          | May depend on                | Must not contain                                 |
| ---------------- | ---------------- | ---------------------------- | ------------------------------------------------ |
| `@roe/shared`    | browser and Node | nothing                      | DOM, Node APIs, React, three.js, `Math.random`   |
| `@roe/game-data` | browser and Node | `@roe/shared` (types)        | logic beyond simple derived values               |
| `@roe/sim`       | browser and Node | `shared`, `game-data`        | rendering, UI, cosmetic-only data (grass, props) |
| `@roe/client`    | browser          | `shared`, `game-data`, `sim` | authoritative game decisions                     |
| `@roe/server`    | Node             | `shared`, `game-data`, `sim` | rendering or UI code                             |

### `@roe/shared`: types and rules

Pure functions and types: IDs, vectors, constants (`SIMULATION_TICK_RATE`, `MAX_PLAYERS`), the seeded RNG (`createRng`), stateless value noise (`fractalNoise2D`), and map generation:

- `createHeightField(map).getHeightAt(x, z)` returns the terrain height at any point, with lakes already carved in (`createBaseHeightField` is the natural terrain before water). The heightmap is never stored or sent over the network; it is recomputed from the map seed. Use it for everything that sits on the ground: the terrain mesh, decorations, units, buildings and the camera focus.
- `flattenHeightField(heights, footprints)` wraps a height field so the ground under each placed footprint is perfectly flat (levelled to the original height at its center) and blends back to the terrain within a few units. A building's own footprint always wins over a neighbour's blend band. Settlement buildings use it now; player construction will reuse it.
- `scatterDecorations(map, { heights, isBlocked })` places trees and rocks. Trees cluster into forests through a noise mask, and the central settlement area (`map.settlement`) stays empty. `heights` lets them sit on flattened terrain, and `isBlocked` keeps them off buildings and paths.
- `sampleCatmullRom(points, spacing)` and `distanceToPolyline(...)` define path shapes the same way on every machine.
- Water: lakes are hand-authored in `map.water` (center, radius, depth, shoreline irregularity). `resolveLakes` derives each water level from the natural terrain, just below the lowest point of its shoreline, so water can never spill. `carveLakes` cuts the basin and banks into the height field. `createWaterMap(...).isWater(x, z)` is the shared water lookup: decorations never spawn in water.
- `createBuildRules(map).isBuildable(x, z)` is the construction rule for Phase 3: inside the playable area and not in or right next to water.
- Map layout, from the center outward: the flat settlement plateau, rolling hills across the playable square (`map.size`), then a non-playable border ring (`map.border`) of forested mountains. The mountains continue past the ring and fade into the fog, so the world never visibly ends. `isInPlayableArea(map, x, z)` tells the two zones apart. Border trees are scenery only.

Determinism is required. With the same input, a rule function must return the same output on every machine. Always use `createRng(seed)` and never `Math.random()`.

### `@roe/game-data`: definitions

Static configuration written as typed object literals with `as const satisfies SomeDefinition`. That keeps literal types while still checking the shape. Races, upgrade tiers, units and spells will go here too. Current contents:

- `PROTOTYPE_MAP`: terrain, forest, border and water (one lake) settings.
- `BUILDINGS`: id, name, `modelPath`, `footprint` (world units), `scale` and `rotationOffset`. Footprints are measured from model bounding boxes. By convention every building's entrance faces local +Z.
- `PROTOTYPE_SETTLEMENT`: the hand-authored starting village around a central square. Fields are tiled `farm_plot` instances built with `field()`. Paths are spline control points whose endpoints come from `entrancePoint()`, so moving a building keeps its path attached; every path ends at an entrance or runs off toward the map edge as a road. The layout also lists squares (worn ground) and prop rules.
- `RESOURCES`: wood, stone, iron, gold, food and mana. Building `cost` uses wood, stone and gold so far.
- Buildings also carry `buildable`, `cost` and `description`. A `field` is one placeable 2×3 unit of `farm_plot` tiles (`modelTiling`).
- `PROPS`: small pack details (rocks, garden trees). The pack has no standalone village clutter; barrels, crates and fences are baked into the building models.
- `MEDIEVAL_PACK`: the KayKit asset pack's folder, its world scale (pack unit × 3) and material overrides (color, roughness) by material name. The overrides are applied when models load, so the GLB files stay untouched.

### `@roe/sim`: game simulation

Game rules that need both primitives (`shared`) and content (`game-data`). `shared` can't import `game-data`, because `game-data` already depends on `shared`, so this layer sits on top of both. Client and server import it and run exactly the same code.

- `createWorld(map, settlement)` builds the static, gameplay-relevant world: the terrain with lakes (`terrain`), the terrain flattened under the starting settlement (`heights`), the water map, the starting buildings, sampled paths, trees and rocks with stable ids, and the map's ore `deposits` (`MapDefinition.deposits`: kind gold or iron, center, radius, and an `amount` unused while deposits are infinite). Trees and rocks keep clear of deposits (radius + 5), so a mine always fits.
- **Game state** (`GameState`) is plain, serializable data: the tick number, building instances (id, type, position, rotation, owner, `status: construction | complete`), construction progress per site, units, each player's resource stock (`stocks`, whole numbers for every resource: the six main ones plus the goods grain and flour), the remaining amounts of harvested trees and rocks (`resourceNodes`, sparse by decoration id: absent = untouched, 0 = depleted), the fields (`fields`, by building id: `{ phase: sowing | growing | harvesting, plotsDone, ripeAt }`; absent = fresh, to be sown) and the next entity id. Units carry goods in `carrying` (`{ resource, amount }` or null). The starting settlement becomes the first instances (complete), followed by the starting serfs in front of the first Town Hall; its fields start ripe. `createInitialState(world, { owner, players, resources })` gives the starting settlement to a player (the client uses the local player; the server keeps it neutral until matches have start positions) and a starting stock (`STARTING_RESOURCES` from game-data) to the owner and any further listed players. Construction progress lives in `construction` (by site id), not on the building, so the `buildings` array only changes when buildings are placed or finished and terrain or instancing never rebuild for progress. `createStateHeights(world, state)` is the terrain flattened under every building in that state.
- **Simulation context** (`SimContext`): the derived caches, the flattened `heights`, the nav grid and an A* path finder. It is not state and is never sent: client and server each build it with `createSimContext(world, state)`. `syncContext(ctx, state)` keeps it in step (new buildings are stamped incrementally, except walkable ones; newly depleted trees and rocks are cleared from the nav grid with `removeDecoration`, which re-stamps overlapping neighbours). It is the only mutable part of the simulation.
- **Tick** (`stepGame(ctx, state, commands)`): advances the game by one fixed step (`SIMULATION_TICK_RATE` = 10 Hz). Queued commands are applied first, in order, then: arrows landing → serf behavior (tasks) → worker loops → fighters (`combat/fighting.ts`) → the tick's damage and deaths → routes crossing new buildings are dropped → path planning (at most 24 searches per tick, oldest units first) → walking → separation → construction work → workers hired → corpses removed → end-screen numbers counted and outcomes decided. Units are shallow-copied once per tick and mutated as working copies; the input state is never touched. Same state and commands give the same result on every machine (no `Math.random`, ids decide ties). Speeds are in units per second, converted to ticks in one place, so the tick rate can change later.
- **Units** (`UnitInstance`): id, type, owner, position, a task (`idle`, `move`, `build` with site and work slot) and a movement (goal, waypoints, stuck counter). Serfs (`units/serfBehavior.ts`): finished moves become idle; idle serfs look for work once per second (staggered by id) and take the nearest own construction site with a free work slot within 30 units; builders work while they stand within reach of their site. A serf caught under a newly placed site steps out of it.
- **Construction:** every working serf adds 1 work per tick; a site needs `buildTime × tick rate` work (`buildTime` and `maxBuilders` come from game-data), so builders speed it up linearly. Work slots (`workSlots`) are `maxBuilders` points spread around the footprint, starting at the entrance, which caps the number of builders. Finished sites become `complete` and free their builders.
- **Pathfinding** (`nav/`): a 1-unit walkability grid over the playable area (57,600 cells on the prototype map) blocks steep cells, water, the border, trees and rocks (by radius plus clearance) and building footprints (except `walkable` buildings: fields, which units cross and farmers work on; they still block placement), each layer in its own flag bit so buildings and depleted nodes can be updated independently. A* uses 8 neighbours without corner cutting, integer costs and an octile heuristic. Its typed-array buffers are reused via generation stamps, and its heap breaks ties deterministically. Blocked goals snap to the nearest walkable cell; unreachable goals end at the closest explored cell, capped at 30,000 expanded cells. Routes are then smoothed by line of sight (string pulling). Measured on the prototype map: about 1–1.5 ms per path on average (a cross-map route expands about 6,000 cells), and the nav grid builds in about 30 ms. Flow fields or hierarchical A* can be added behind `PathFinder` when armies arrive.
- **Separation:** units aren't obstacles for path planning. Instead, overlapping units push each other apart each tick (spatial hash, soft push, never into blocked cells; working units hold their spot). Group moves spread their goals in a spiral around the target, and a unit stuck near a crowded goal stops; farther away it re-plans (twice at most).
- **Economy** (`economy/stock.ts`): `stockOf`, `missingResources`, `canAfford` and `pay` work on a player's stock. Placing a building checks the placement rules and the cost (`notEnoughResources`, reported together with the placement issues) and pays the full cost when the site is created. A player without a stock (e.g. on the server's neutral settlement) can't place anything. Phase 5 plan: [phase-5-plan.md](phase-5-plan.md).
- **Material delivery** (`construction/delivery.ts`, `units/building.ts`): the cost is paid at placement, then builders carry it over one unit per trip. Each site's `ConstructionProgress.delivered` counts what arrived; work can't exceed the delivered share of the cost (`allowedWork` = `floor(workRequired × delivered / total)`), so builders stand idle while waiting. A builder without material for its site checks every tick for a missing unit nobody is fetching yet (`missingMaterial`, with an in-transit tally rebuilt from the `deliver` tasks each tick and updated as builders claim units) and fetches it right away, even on its way to the site: `deliver` task to the nearest storage → picks up one unit → back to its work slot (kept while fetching) → hands it in → `build`. Picked-up goods are marked `Cargo.siteId`: they were paid already, so if the trip is interrupted and they end up at a storage they return to the site's reserve instead of the stock (no free resources), and a builder arriving with them hands them in directly.
- **Workers** (`units/workers.ts`): a building with `production` in game-data gets one worker once it is complete and its owner has free housing (`hireWorkers`, run at the end of every `stepGame` tick and by `createInitialState`; buildings are served in id order, and a building that has to wait is simply checked again next tick). `production` is a discriminated union by `kind`, and `updateWorkers` hands each worker to the loop of its kind (`units/production/`, shared helpers in `common.ts`). The `work` task keeps the phase, a `target` (node id or plot index) and the ticks of work on the current step.
  - **`harvest`** (`harvest.ts`; lumbermill: trees within 25 units, quarry: rocks within 30): the node nearest the building with something left → harvest (same timings as serfs) → back to the building → process (`processSeconds`) → nearest storage → deposit → next node; with nothing in reach it waits and looks again every 2 s.
  - **`farm`** (`farm.ts`; field): the field's plots are its model tiles (`tileOffsets`, shared by sim and renderer). The farmer walks to each plot's work point in the middle furrow (`plotWorkPoint`) and sows it (`sowSeconds`); after the last plot the field is `growing` with `ripeAt = tick + growSeconds`, and the farmer waits at the field. Once ripe, it harvests plot by plot (`harvestSeconds`), 1 `crop` (grain) per plot, and walks to storage once the load reaches the profession's `carryCapacity` (game-data `PROFESSIONS`; farmer 3, everyone else 1) or the field is done; after the last plot the field is fresh again. The field's progress lives in `GameState.fields`, written through the economy draft (`setField`), so it only changes when a plot is done; storing the ripening tick instead of a countdown keeps the state unchanged while the crop grows.
  - **`process`** (`process.ts`; mill: 1 grain → 1 flour in 4 s, bakery: 1 flour → 2 food in 6 s): when the owner's stock holds input, the worker takes it out of the stock as they set off (`withdraw`, a reservation: no two workers count on the same unit), fetches it from the nearest storage (`fetching`), works on it at the building and carries the output back; standing at storage after a delivery, it picks up the next input right there. A trip takes as many steps as the profession's `carryCapacity` allows for input and output alike (`stepsPerTrip`: miller 3, baker 2 because each flour makes 2 food and the baker carries 4); `target` holds the trip's steps. A fetch that can't reach the storage refunds the input; input that can't reach the building is carried back to storage. A test checks every tick that one grain is in exactly one place (stock, reserved, in hand, or as flour).
  - Workers aren't controllable (`UnitDefinition.controllable`): commands ignore them and the client can't select them.
- **Population** (`economy/population.ts`): derived, never stored. `populationOf(state, player)` counts the player's units (serfs and workers each take one place) against the `housing` of their complete buildings (game-data: Town Hall 10, house 4; construction sites house nobody). Recruiting and hiring workers both need a free place, so a full population is fixed by building houses, never by losing units.
- **Combat** (`combat/`, stats in game-data `units/combat.ts` and `UnitDefinition.combat`): every unit has integer `health` and a `diedAt` tick; units that fight (an `attack` definition) also have a `combat` state: `targetId`, `readyAt` (next attack), `strikeAt` (the tick the attack in progress hits or releases its arrow) and an `anchor` (where a unit that engaged on its own returns, and what its 12-unit leash is measured from). Timers are tick numbers, so they don't change every tick. **Damage** = `max(1, round(damage × bonus[target armor class] − armor))` (`damageAgainst`); a tick's hits are summed per target (`Hits`) and applied at once (`applyHits`), so the order in which attackers act doesn't matter. **Fighters** (`updateFighters`, state order): a strike that is due lands first (melee: damage, if the target is still within reach + 0.5; ranged: an arrow); then the target is kept, taken from an `attack` order, or found: idle units (not while walking back) and attack-movers scan every 3 ticks (staggered by id) within their `sightRange` through a per-tick point grid of living units, preferring enemies already attacking them, then the nearest, ties by id (`findTarget`). Out of reach they chase (a straight route when the line is clear, otherwise the path planner; re-planned when the target moved 1.5 units from the route's goal); in reach they stand and start an attack when `readyAt` allows (strike after `windup`, next attack after `cooldown`). Attack-movers resume their walk after each fight; units on a plain move ignore enemies. **Arrows** are records in `GameState.projectiles` (`attackerId`, `ownerId`, `targetId`, release point, `firedAt`, `impactAt` from distance ÷ speed, damage worked out at release): they home and land on `impactAt` if the target still lives; the client only draws them. **Death:** a unit at 0 drops its task, route, target and cargo, gets `activity: 'dying'` and lies for `corpseSeconds` (3 s) before it is removed; dead units are skipped by behavior, separation, targeting, commands and the population. **Hostility** (`areEnemies`): units of different non-null owners; `MONSTER_PLAYER` (`monsters`) is reserved for camps and waves. **Dev spawn:** `debugSpawn` is accepted only by a context created with `{ dev: true }`; the server never creates one.
- **Training** (`training/training.ts`): buildings with `trains` in game-data (barracks: swordsman, spearman; archery range: archer) keep a queue in `GameState.training` (by building id: `{ queue, readyAt }`, absent when empty). `trainUnit {buildingId, unit}` checks the issuer's own complete building, that it trains the unit (`cannotTrain`), a free place in the queue (`queueFull`, 5) and the cost, pays it, and appends (a unit queued into an empty queue is ready at `tick + trainTime`). `cancelTraining {buildingId, index}` refunds that unit (`notQueued` otherwise); cancelling the head restarts the next from scratch. `progressTraining` runs after the workers are hired each tick: in building-id order, a due head leaves the building at `spawnPoint` when its owner has free housing (otherwise the queue waits), and the next starts; queues of buildings that no longer stand complete are dropped. The records only change on those events.
- **Buildings in combat** (`combat/buildings.ts`): buildings share the entity id space with units, so `combat.targetId`, `attack` orders and arrows name either. A fighter's target is a `Foe` (unit or building): reach to a building is the distance to its footprint (`buildingReach`), and attackers walk to `approachPoint` (the footprint point nearest to them, 0.6 outside; the planner snaps it to a walkable cell). Auto-engage takes enemy units first, then the nearest enemy building within sight (`findBuildingTarget`). Damage is stored as **damage taken** (`GameState.buildingDamage`, by id), not remaining health, so a construction site's health (`buildingMaxHealth`: `siteHealthShare` 10% growing to 100% with the work) can rise without any healing logic. `applyBuildingHits` runs after the economy commit each tick: buildings whose damage reaches their health fall: they leave `buildings` (with their `construction` and `fields` records and damage), their worker dies, and they become a `Ruin` (`GameState.ruins`: id, type, position, rotation, owner, tick). `createStateHeights` flattens under ruins too, so terrain heights don't change when a building falls (the client's terrain mesh stays as it is). `hireWorkers` skips buildings with a living enemy unit within 15 units (otherwise a besieged building would keep sending out free workers).
- **Monster camps** (`combat/camps.ts`, `combat/bounty.ts`): `MapDefinition.camps` (shared: center and `{ unit, count }` with game-data unit ids) are spawned by `createInitialState` for `MONSTER_PLAYER`, spread around the center; each guard's spot becomes `UnitCombat.home`, which a guard uses as its anchor whenever it engages on its own (leash and walk back), so the idle-unit rules of 6.1 make it a guard with no extra behavior. Monster kinds (`skeletonMinion`, `skeletonWarrior`, `skeletonArcher`: armor class `monster`, not controllable) carry a `bounty`. `Hits` remembers the owner of the last hit per target in a tick (state order, deterministic); `applyHits` returns the deaths with that killer, and `payBounties` deposits the bounty into the economy draft for killers who have a stock.
- **Waves** (`combat/waves.ts`): `MapDefinition.waves` (shared: time in seconds, spawn point, units) are sent by `sendDueWaves` at the end of the tick they are due (`GameState.wavesSent` counts sent waves, `lastWaveAt` remembers the tick for the client's banner). A wave spawns for `MONSTER_PLAYER` around its point and attack-moves (spread like a group move) to the player Town Hall nearest to it; attack-move scanning includes buildings, so it razes what lies on the way, and at the end its units are idle fighters that keep attacking whatever comes into sight. The dev-only `debugWave` sends the next wave at once. The client's `WaveAlert` shows a countdown during the last minute and a banner for 8 s after a wave sets out.
- **Win and lose** (`rules/outcome.ts`): `GameState.outcome` holds `{ result: 'won' | 'lost', at }` per decided player (no entry while the game goes on) and never changes once set. `decideOutcomes` runs at the end of `stepGame`, for players with a stock. Defeat (checked first): the player had a Town Hall and has none. Victory: the player has a Town Hall and the map's `objective` is met; `clearMonsters` means every wave sent and no living monster, and it is never met on a map without camps or waves. `GameState.stats` counts soldiers trained, enemies killed and buildings lost as they happen. `validateCommand` rejects a decided player's commands with `gameOver` (the dev commands excepted); the tick keeps running. `viewOf` does not include `outcome` or `stats` yet: Phase 10 has to add the viewer's own before sending views. The client's `OutcomeOverlay` shows the local player's result.
- **Walls** (`rules/walls.ts`, numbers in `BUILDINGS` and `WALL_RULES`): a wall segment is an ordinary building with `wall: true`, so construction, damage, ruins, fog ghosts and attacks work unchanged. Segments are drawn, never placed singly: `placeWall {building, from, to}` takes two grid points on one of 8 directions. A straight segment spans 2 units; a diagonal one 2 along both axes (`footprintOf` makes it √2 longer), so every center stays on the 1-unit grid. The footprint is 1 deep, which with the nav clearance blocks a solid strip along diagonals too. `planWall` checks each segment against the ground (`checkGround`: walls may cross paths, need no gap to buildings and may touch walls); `budgetWall` then pays for the valid ones in line order from the drag's start; the command builds and charges those, skipping blocked, already standing and unaffordable ones, and fails only when not one segment can be built and paid. Walls don't flatten the terrain (`createStateHeights`), so drawing or losing them keeps the same height field. Fallen segments don't count as lost buildings. `findCutOff` (`rules/enclosure.ts`) compares the nav grid's connected regions before and after a planned line and reports the player's units and sites that would lose their way to the largest region: a warning, not a rule (0.7 ms for 40 segments on the 120 × 120 test map).
- **Gates:** a gate is a wall segment type with `gateOf` (its wall type). `makeGate {segmentId}` replaces an own, undamaged segment with a gate construction site under a new id (a segment still being built is refunded; material carried for it is dropped, so it isn't paid back twice). A finished gate stamps its cells on the nav grid with a `GATE` flag and its owner (`NavGrid.gateOwners`); a cell shared with anything solid or another player's gate stays blocked. Every walkability question takes a `Passer` (whose unit is asking): `findPath`, line of sight, smoothing, separation, stepping out of obstacles, the client's move cursor. Without one, gates are closed. `syncContext` restamps when a gate finishes or falls. A 2-unit gate leaves a passage two cells wide, straight or diagonal. `findCutOff` treats the player's gates as open, also unfinished ones. On the client, `GateDoors` draws the model's door nodes in their own instanced meshes and swings them around their hinges while the owner's units are near (cosmetic).
- **Breaching** (`combat/breaching.ts`, `BREACH_RULES`): auto-targeting never picks walls (`findBuildingTarget`). Instead the route planner decides: for a fighter on an attack or attack-move (or with a target) whose route ends more than 1.5 units short of its goal, it searches again with `breach: true`, where cells covered only by enemy walls are passable at a very high cost (10,000 per cell, plus 10 per hit point of the segment), so any way around wins and weak segments are preferred. The first wall on that route becomes `UnitCombat.breachId`; the fighting code attacks it until it falls (turning on enemy units it can walk straight to), then the unit resumes its order. Performance, all deterministic: a per-passer region cache (`nav/regions.ts`, flood fill after the grid changes) skips searches that can't succeed; units in the same 8 × 8 square with goals in the same square share one decision per tick; at most 3 breach searches run per tick, others wait. Ranged units whose target is already in range shoot over walls. `viewOf` hides `breachId` of others.
- **Towers** (`combat/towers.ts`; every number is `BuildingDefinition.tower` in game-data): a complete building with `tower` shoots by itself. `updateTowers` runs after the fighters: a tower whose cooldown (`GameState.towerCooldowns`, the tick it may shoot again) has passed looks for a target on its scan tick (`towerTarget`: enemy units within range of its center, attackers first, then nearest, then lowest id) and adds an ordinary projectile with `fromHeight`, so arrows, damage, kill credit and bounties work as for archers. On the client, `rangeRing` is a terrain-following ring (ghost and selected own tower), `BuildingDefinition.tint` recolors a model (`tintedMaterial`; the team cell keeps the owner's color).
- **Answering towers** (`combat/provocation.ts`): `updateFighters` gets the shots in flight as the tick began. The targets of tower shots, and same-owner units within `COMBAT_RULES.alarmRadius`, are "under fire". Such a unit, if idle or attack-moving with nothing else to fight, sets `UnitCombat.provokedBy` and targets the tower; the leash doesn't apply while it is within the tower's range plus `retreatMargin`, and enemy units it can walk up to still come first. If the tower can't be reached by walking or breaching (`createReachCheck`: the region cache, then one breach search per owner, area and tower per tick), an idle unit walks to a point beyond its range, as a walk back that ignores what it sees. Every new order clears `provokedBy` and `breachId`.
- **Vision / fog of war** (`vision/vision.ts`): a `Vision` per player is a cache next to the state (`SimContext.visions`, for the players given to `createSimContext(..., { visions })`; `stepGame` updates them after each tick). It is a grid of 2 × 2 unit cells over the map: `counts` (how many of the player's sight circles cover a cell; > 0 = visible), `explored` (ever seen) and `lastSeen` (other players' and neutral buildings as last seen, kept until their spot is seen again, so a building destroyed out of sight stays a ghost). Sight comes from game-data (`UnitDefinition.sight`, `buildingSightOf`). Updates are incremental: each own unit or building has a stamp (center cell and radius); only units that changed cell are re-stamped (+1 the new circle, then −1 the old), the dead and destroyed are unstamped. `version` changes when any cell turns visible, hidden or explored, for renderers. 200 moving units cost about 0.04 ms per tick.
- **Player views and sight rules** (`vision/view.ts`): `viewOf(world, state, vision)` is what one player may know, and what the multiplayer server will send instead of the state: all of the player's own things; other players' (and monsters') units only on visible cells, stripped of `movement`, move and attack-move goals and guard homes; other buildings as last seen; construction, training, fields and stock of the player only; building damage of own and visible buildings; arrows whose shooter or target is visible; ruins and harvested nodes on explored cells; the public wave progress. A test checks on every tick of a moving battle that no other player's unit outside the viewer's sight appears in a view. `attack` is rejected with `notVisible` when the context keeps the issuer's vision and the target isn't in it. The server keeps a vision per joined player (`ensureVision` on join, `dropVision` on leave); sending views comes with Phase 10.
- **Gathering** (`state/resourceNodes.ts`, `units/gathering.ts`, `economy/draft.ts`): trees and rocks inside the playable area are resource nodes (`RESOURCE_NODES` in game-data: tree 3–5 wood, rock 6–12 stone by size; 3 s per wood, 4 s per stone). A serf's `gather` task loops: walk to the node → work → carry `GATHER_RULES.carryCapacity` units to the owner's nearest storage (`STORAGE_BUILDINGS`: the Town Hall for now) → deposit → back; when a node runs out it moves on to the nearest node of the same kind within 14 units of it. Goods of another kind are delivered first. During a tick, harvesting and deposits write to an `EconomyDraft` (copy-on-write), so `resourceNodes` and `stocks` keep their references in ticks where nothing was taken or delivered.
- **Commands** are what a client sends: `placeBuilding`, `recruitSerf {buildingId}`, `moveUnits {unitIds, x, z}`, `assignBuilders {unitIds, siteId}`, `gather {unitIds, nodeId}` (the nearest serf takes the node, the others spread over nearby nodes of the same kind), `attack {unitIds, targetId}` (fighting units chase one living enemy until it dies; issues `noTarget`, `notEnemy`), `attackMove {unitIds, x, z}` (spread like a move; units that don't fight just walk), `stop {unitIds}` and the dev-only `debugSpawn {unit, count, x, z, owner?}` (issue `devOnly`). Every new order drops a unit's target and leash. A command never contains the player: the receiver attaches the issuer (the server takes it from the network session), so a client can't act for someone else. `parseCommand(unknown)` turns an untrusted message into a command, copying only known fields (unit lists: 1–256 distinct positive integer ids).
- **`applyCommand(ctx, state, issuer, command)`** validates and executes a command purely: it returns a new state, or the unchanged state plus the failed rules (`CommandCheck`). `validateCommand` runs only the checks. Unit commands affect only the issuer's own units (others in the list are ignored); recruiting needs the issuer's complete Town Hall, a free place in the housing and the serf's cost (`UNITS.serf.cost`, 2 food, paid from the stock), and stays under the per-player limit (200 serfs). Placing a building creates a construction site.
- **Placement rules** (`checkPlacement`, tunable via `PLACEMENT_RULES`): a known and buildable type; the center on the 1-unit grid; rotation in whole quarter turns; inside the playable area; not in or right next to water; at most 1.5 units of height difference under the footprint; a 1-unit gap to other buildings (rotated-rectangle overlap test); clear of paths; and not on trees or rocks (depleted ones no longer count). Spatial indexes over trees, rocks and path samples keep the checks fast.
- **Tests:** `pnpm test` runs vitest on small synthetic maps (flat ground, a known lake and path, an injected tilted terrain for the slope rule, a Town Hall with five serfs). They cover placement, commands, the nav grid and A*, serf behavior and construction, the economy (stocks, payment, population and housing), gathering, farming (a full field cycle yields one grain per plot, the farmer waits while the crop grows, fields are walkable, the starting fields are ripe, determinism) (a test map with scattered trees and rocks), determinism (the same commands give a deep-equal state after 400 ticks), and benchmarks that print timings (`[bench]`).

### `@roe/client`: the game client

```text
src/
  main.tsx, App.tsx    bootstrapping and layout (canvas plus HUD overlay)
  render/              everything inside the <Canvas>
    GameCanvas.tsx     renderer, camera and scene root
    camera/            RTS camera (MapControls, key and edge panning, bounds clamp)
    scene/             World, Terrain, Water, Paths, Lighting, Trees, Rocks, Sky
    scene/settlement/  Settlement, ModelInstances (GLB loading, overrides, instancing)
    placement/         PlacementPreview (ghost model, validity), groundPick (ray vs height field)
    simulation/        SimulationDriver (fixed-step tick loop), simClock (interpolation factor)
    units/             UnitFrameDriver (per-frame unit data), Units (baked characters, placeholder fallback)
      baked/           bakeCharacter (bone texture), bakedSkinMaterial (GPU skinning), BakedUnits
    selection/         SelectionMarkers (building frame), SelectionRings (instanced unit rings)
    construction/      ConstructionSites (dirt, scaffold, clipped model, progress bar)
    commands/          CommandMarkers (pooled move/site markers), commandFeedback (input → marker queue)
    picking/           pickBuilding (ray vs oriented building boxes), screenPick (units in screen space)
    shaders/           shared GLSL snippets (value noise)
  world/               decorateWorld: cosmetic layers (props, worn ground, grass) on top of the sim world
  ui/                  HTML/CSS overlay (ResourceBar, ConstructionMenu, SelectionPanel; cursors/ and icons/: original SVGs); never imports three.js
  input/               input hooks (keyboard, placement, selection), pointerTarget, cursorKind, useHoverCursor
  state/               Zustand stores: gameStore (simulation), placementStore, selectionStore and settings (UI only)
```

Rules:

- **`render/` only visualizes.** It reads state and draws it. It does not compute gameplay outcomes.
- **`ui/` is plain React DOM** that sits over the canvas. It talks to the scene only through stores.
- **Per-frame values never go through React state.** Camera movement, animation and similar values are mutated inside `useFrame` or kept in refs, which avoids re-renders. Zustand stores hold values that change at human speed, such as settings, selection and menus.
- **Static props use chunked instancing.** `StaticInstances` uploads instance matrices once. Trees are split into 60×60 world-space chunks, each its own instanced mesh with its own bounding sphere, so chunks outside the camera or shadow frustum are skipped. Chunks share one geometry and material per part.
- **The world comes from `@roe/sim`.** `createWorld` (sim) builds the gameplay world, and the client's `decorateWorld` adds the cosmetic layers: props behind and beside buildings, worn-ground patches and ground cover. Every renderer and the camera sample the same `world.heights`.
- **Hexagon buildings: team colors, variants, yards.** The Hexagon pack's models share one atlas (an 8 × 4 grid of gradient swatches). Its four color variants differ only in the swatch of the roofs, banners and trims, which is cell [2, 3] in the yellow variant we ship: found by diffing the UVs of the yellow and blue variants of every model (the only vertices that change), and confirmed that no other vertex uses that cell (`HEXAGON_PACK.teamCell`). `teamColorMaterial` clones the atlas material and replaces `color_fragment`: in that cell the instance color (`instanceColor`, set by `ModelInstances` and `SpinningParts` from the owner, negative = keep for neutral) replaces the texel, scaled by the texel's brightness over the cell's mean (the characters' atlas tint formula); elsewhere the instance color is ignored. three.js defines only `USE_COLOR` (not `USE_INSTANCING_COLOR`) in the fragment shader, and `vColor` is a `vec4`. `modelVariants` (houses: home_A, home_B) are picked by building id (`modelPathOf`), so the ghost can show the variant of `state.nextEntityId`. Buildings with `yard` get two worn patches (`world/yards.ts`): around the base (half-diagonal + 2.5) and in front of the entrance; the starting village gets them in `decorateWorld`, placed buildings when `Terrain` re-colors their region (it holds the patch list and extends it first). Every model's entrance faces +Z (checked with front and back renders), so `rotationOffset` stays 0.
- **Assembled buildings** (`BuildingDefinition.parts`: the storehouse): a list of prop models with local offsets, rotations, scales and heights. `Settlement` turns each part into an instance of its own model (grouped with every other use of that model), so an assembled building costs no extra draw calls per copy; the ghost clones the parts. `modelFilesOf` lists the files any building needs (variants or parts) for preloading.
- **Buildings are instanced per model part.** `Settlement` groups buildings and props by model file. `ModelInstances` loads the GLB with `useGLTF` (preloaded, no Draco), applies the material overrides, and draws each mesh of the model as one instanced mesh, so six houses cost the same draw calls as one. A building's `cropMesh` (the field's `farm_wheat`) is left out and drawn by `FieldCrops`: one instance per plot of every complete field, scaled and tinted by a discrete stage derived from `GameState.fields` and the tick (bare → sprouts → five growth levels from green to golden → stubble). Ripe crop is 60% of the model's height so the farmer stays visible (`RIPE_CROP_HEIGHT` in `cropHeight.ts`); construction sites and the placement ghost lower the crop node of their cloned tiles the same way (`lowerCrop`). A building's `spinningPart` (the mill's `mill_blades`) is also left out (nodes are skipped with everything under them, since a multi-material glTF mesh loads as a group) and drawn by `SpinningParts`: one instanced mesh per part, turning around its node's hub while the building is busy (`busyBuildings`: a worker is processing; cached per units array), easing up to `turnsPerSecond` and back to a halt. `ChimneySmoke` emits puffs from `smokeFrom` (model units) of busy buildings: one instanced mesh for up to 96 puffs that rise, drift, swell and shrink, driven by frame time. Millers and bakers are hidden while processing (`RenderedUnit.inside`): they work inside. Instances are rewritten in `useFrame` only when a plot's stage changes; bare plots get a zero matrix. Paths are one soft-edged (vertex alpha) ribbon mesh; worn ground is baked into the terrain vertex colors.
- **Ground cover is cosmetic and instanced.** `world/groundCover.ts` places grass tufts and flower clusters on a jittered grid: some grass everywhere, lush in noise-masked meadows, thinning near paths, and none on paths, buildings, fields, worn ground or water. Each grass instance is a small patch of 10 short blades (0.25–0.45 units tall), so the ground reads as a carpet. `GroundCover` draws them in 40×40 chunks without shadow casting. In the vertex shader, a shared wind clock drives a cheap sway, and ground cover shrinks into the ground between 100 and 140 units from the camera; chunks entirely beyond that are hidden on the CPU.
- **Shaders are small and procedural.** The terrain keeps its vertex-color zones (grass, dirt, rock, worn ground, sand, lake bed) as the base; an `onBeforeCompile` patch on its standard material adds subtle world-space noise detail that fades with camera distance. Visible grass detail comes from the instanced ground cover. Water is a custom `ShaderMaterial` (color and opacity by depth, a thin shoreline foam line that gently moves in and out, fog; the open surface is deliberately calm). No textures are downloaded.
- **Simulation state vs. rendering.** `gameStore` holds the `@roe/sim` world, the `SimContext`, the current `GameState`, the state one tick earlier (`previous`) and the state heights. `dispatch(command)` validates immediately (for UI feedback) and queues the command with the local player as issuer; `advance()` runs one `stepGame` tick with the queue, exactly like the server. Later `dispatch` will also send the command to the server. The store changes 10 times per second, so subscribers select narrowly: `state.buildings` and `heights` keep their references unless buildings change, which keeps terrain, instancing and React from redoing work every tick. UI-only state (the construction tool, the selection) lives in `placementStore` and `selectionStore` and is never sent anywhere. The placement ghost validates with `validateCommand` (placement rules plus cost, exactly as the server) and re-checks when the cell, rotation, buildings or the local stock change. The `ResourceBar` selects the local player's stock object, which only changes on payments and deliveries, and flashes each +/- delta (previous stock kept in state, compared during render). Resources have a `category` in game-data: the six `main` ones come first, the `goods` (grain, flour) follow as a smaller group (`resourcesIn(category)`).
- **Tick loop and interpolation.** `SimulationDriver` (mounted first in the canvas) advances the simulation from the render loop with a fixed-timestep accumulator: one `advance()` per 100 ms of frame time, at most 250 ms caught up after a pause (a hidden tab pauses the game). It publishes `simClock.alpha`, how far rendering is between the previous and the current tick. Renderers interpolate positions with it, so units move smoothly at any frame rate, one tick (100 ms) behind the simulation.
- **Units are instanced and never re-render React.** `UnitFrameDriver` (mounted right after `SimulationDriver`) computes every unit's frame once: interpolated position, ground height, smoothed facing (walking direction, or the site while building) and activity, published in `renderedUnits` / `renderedUnitList`. Unit renderers, selection rings and screen picking only read that.
- **Stumps** (`Stumps`): felled trees (amount 0) get one of the pack's two stumps (by tree id) at `stumpScale` × the tree's scale; two instanced meshes. The state doesn't time felling, so the client notes when it first sees each stump (module map) and sinks it into the ground after 180 s (20 s); stumps under player buildings are skipped. Matrices are rewritten only when the list changes or while one sinks. They never block: the sim already treats depleted trees as gone.
- **Trees and rocks follow `resourceNodes`.** `World` passes the node amounts to `Trees` and `Rocks`. A tree chunk that lost a tree is repacked (cached per chunk by standing-tree count and ground, so other chunks keep their buffers); rocks are one instanced mesh, repacked on change, and shrink with the amount left (down to 45% before they vanish). `UnitFrameDriver` turns gatherers toward their node and gives each rendered unit a `work` kind (build, chop, mine) that picks the clip (`Hammering`, `Chopping`, `Pickaxing`).
- **One instanced character per unit kind.** `BakedUnits` bakes each villager character (`CHARACTER_PACK.serf` / `.worker`, sharing `VILLAGER_ANIMATIONS`) and `villagerInstances.update` writes only the rendered units of its kind, with that kind's speed for the stride-matched rates.
- **Carrying.** The pack has no carry walk, so `combineClips` builds one at load time: `carry` keeps `Walking_B`'s legs and hips and takes the spine, head and arms (`RIG_MEDIUM.upperBody`) from the `Holding_A` pose (both forearms forward); `hold` is `Holding_A` alone, for standing with a load. Both are baked like any clip; `carry` keeps the walk's stride, so its playback rate is stride-matched too. Carried goods are our own low-poly meshes built in code (`carryBundles`: three logs, three stones, or a sack for the other resources). `bakeCharacter` measures a `CarryAttachment` from the first carry frame: the point between the hand slots, expressed in the `chest` bone's bind space. Each bundle geometry is moved there and rigidly skinned to that bone (skin index = chest, weight 1), so the same baked-skin material animates it with exactly the unit's clip, phase and rate. One instanced mesh per bundle shape (one draw call each while anyone carries); `serfInstances.update` writes bundle instances in the same loop as the serfs. Loads are hidden while a unit works.
- **Character models with baked animation.** Serfs (and, the same way, workers: the Rogue without cape) are KayKit Adventurers characters (`CHARACTER_PACK` in game-data: the Ranger without cape and quiver, scale 0.62 (~1.4 units tall), clips per activity including the combined `carry` and `hold`). Three.js can't instance skinned meshes, so `bakeCharacter` prepares them once at load time:
  - It merges the visible body parts into one geometry, pre-transformed by their bind matrices, with skin indices remapped by bone name.
  - It samples every clip at 30 fps into a float "bone texture": one row per frame, four texels (matrix columns) per bone, holding `bone.matrixWorld · boneInverse`.
  - `bakedSkinMaterial` patches a `MeshStandardMaterial` (and a matching depth material for shadows) so the vertex shader skins each instance from that texture. Per instance, `aAnim` holds the clip's first row, frame count, a phase offset and the playback rate; neighbouring frames are blended.
  - All serfs are one instanced mesh: one draw call, plus one for shadows. Lighting, fog and shadow receiving stay three.js's own.
  - **Atlas tint:** KayKit characters color their texture with an 8 × 4 grid of swatches. `CharacterModel.tint` lists the swatch cells that take the owner's color (`team`: the serf's blue scarf, the worker's neckerchief and cuffs) and the profession's tunic color (`profession`: the worker's tunic). The fragment shader picks the role from the UV cell (exact, no color guessing) and keeps the swatch's shading: the new color is scaled by the texel's brightness divided by the cell's mean brightness, measured once from the texture at load. Per instance, `aTeam` and `aTint` carry the two colors.
- **Attached props** (`attachedProps.ts`): loads, hats and tools are low-poly meshes rigidly skinned to one bone (weight 1) and drawn as one instanced mesh per shape with the unit's transform and animation attributes, so they follow the body exactly; a mesh with no instances this frame is hidden. Loads (`carryBundles.ts`: logs, stones, sack, bread basket, gold and iron ore) sit between the hands as posed in `carry`. Hats (`professionProps.ts`, one per `HatStyle`) sit on top of the vertices skinned to the head bone. Tools are held by `handslot.r` in that bone's bind frame, the frame KayKit accessories are modelled in (grip at the origin, handle along +Y): the Adventurers axe (packed to GLB with `scripts/gltf-to-glb.mjs`) and a code-built hammer and pickaxe. Which tool shows follows the work (`build` → hammer, `chop` → axe, `mine` → pickaxe, `reap` → a code-built sickle; `sow` is done by hand). Farmers play `Working_A` while sowing and `Working_B` while reaping and face the plot's center. Grain is carried as a tied sheaf, flour as a sack.
- **Soldiers** (`CHARACTER_PACK.soldiers`: Knight, Barbarian, Rogue_Hooded at 0.71 = 1.15× villagers; `soldierInstances.ts`) are baked like villagers (one instanced mesh per kind, the owner's color in atlas cells found by measuring each model's UVs per cell and its texture), with clips `idle`, `walk`, `attack`, `ready`, `death`. `AnimationClipRef.then` joins two clips at load time (`sequenceClips`: the archer's draw, then release). **Attack timing:** `UnitFrameDriver` gives each rendered unit `attackElapsed` = (render tick − (`readyAt` − cooldown ticks)) / tick rate, where render tick = `state.tick − 1 + alpha` (rendering runs one tick behind) and `combatTicks` is the sim's own conversion; the attack clip is placed at `attackElapsed × attackHitAt / windup`, so its hit frame (`attackHitAt`, set per soldier) meets the strike tick, then `ready` loops until the next attack. Clip times that are set directly use rate 0 in `aAnim` (`onceAt`), so the shader shows exactly that frame; death works the same way (`deathElapsed` from `diedAt`) and holds its last frame, and corpses sink from 1.8 s (`r.y` lowered in `UnitFrameDriver`, so rings and picking follow). Attackers face their target. **Gear** (`soldierProps.ts`): KayKit sword, shield, bow and quiver (packed to GLB; all meshes of an accessory merged, morph targets dropped) and a code-built spear, each placed in its bone's bind frame (hand slots; the quiver on `chest` with an offset) and drawn as attached props. **Arrows** (`render/combat/Projectiles.tsx`): one instanced mesh of the KayKit arrow; each `GameState.projectiles` record flies a shallow arc (peak 12% of the distance) from its release point to the target's interpolated position by the share of its flight time passed, pointing along the arc's tangent; a vanished target keeps its last position.
- **Attack input:** `pickPointerTarget` also returns `enemyId` (a living enemy unit under the pointer, screen-space like own units, only when no own unit is there). `commandIntent(target, fighters)` puts `attack` first when the selection has fighters (`selectionKinds`); `cursorFor` shows the sword (`attack.svg`). F sets `commandModeStore.mode = 'attackMove'` (UI-only), which makes the next left click an `attackMoveIntent` (enemy → `attack`, reachable point → `attackMove`) instead of a selection; Esc or a right click clears it, and it ends when no selected unit fights. X dispatches `stop`. Attack feedback reuses the move marker in red (`CommandFeedback.attack`). `UnitPanel` prunes units that died from the selection (store subscription, once per tick).
- **Ruins** (`render/scene/Ruins.tsx`): rubble from `GameState.ruins` drawn with the shared `ModelInstances` (the Hexagon `building_destroyed`, uniformly scaled to 90% of the footprint; hidden under a building placed on the spot later), and dark smoke for 45 s of game time through `SmokePuffs` (the puff pool extracted from `ChimneySmoke`, which now only supplies its emitters and style).
- **Walls on the client:** `render/walls/Walls.tsx` draws every known wall segment, finished or not: one instanced mesh per wall model and 24-unit chunk, so draw calls don't grow per segment. `BuildingDefinition.wallModel` (game-data) says how the pack model is turned, centered and stretched to a segment (the GLBs are unedited; `ModelInstance` has `stretch` and `local` for this). A site is the same model grown in 8 steps (one string selector, so walls re-render only when a segment grows a step); walls don't use `ConstructionSites`. `wallLayout.wallPosts` puts a post wherever a wall ends, turns, branches or changes material. Ruins of walls are stretched rubble without smoke, health bars are narrow, and the terrain and yard code skip walls. `render/placement/WallTool.tsx` is the drawing tool: pointer events for the drag (it starts on a nearby wall end), `snapWallLine` + `planWall` + `validateCommand` + `findCutOff` for the preview, recomputed only when the snapped line, buildings, stock or felled trees change. `ui/WallHint.tsx` shows the total cost, what is left out and the cut-off warning.
- **Fog of war rendering** (`render/fog/`): `FogPass` takes over the frame (`useFrame` priority 1, so R3F no longer renders by itself): the scene goes into a 4× multisampled half-float render target with a depth texture, then a full-screen quad rebuilds each pixel's world position from depth (inverse projection, camera matrix) and darkens it by the fog texture: one R8 texel per vision cell, linear filtering for soft edges, 0 unexplored (black), 0.5 explored (dim and greyish), 1 visible. Outside the grid (the border mountains) counts as explored; the sky (depth 1) is untouched. The quad applies tone mapping and the sRGB conversion itself, because three.js does both only when rendering to the screen. The texture eases toward the vision (`FADE_RATE`) and uploads only while it changes. `knowledge.ts` decides what the player knows: `shownAt` (own things always, others only on visible cells) filters `UnitFrameDriver` (hidden units are not in `renderedUnits`: no drawing, rings, bars, picking), arrows and building health bars; `knownBuildings` (own + `lastSeen`, cached per buildings array and vision version) is what `World` draws (instancing, sites, crops, animations) and what pointer picking uses, while terrain and cosmetic layers keep the real buildings. Ruins show once explored. The dev-only "Reveal map" setting turns the fog off for rendering.
- **Health bars** (`render/combat/HealthBars.tsx`; damaged buildings get a bar 3× as wide, widened through the instance's X scale, above the roofs): one instanced quad mesh; the vertex shader spreads each quad in view space around its instance position (billboard), the fragment shader draws frame, fill (health fraction in `aBar.x`, colored by it) and background; `aBar.y` marks own units (frame color). Drawn without depth test after everything else. Health and selection lookups are rebuilt only when their arrays change. The GPU objects live in a plain factory (`createHealthBars`), so `useFrame` only calls `update`.
- **Training panel** (`ui/TrainingPanel.tsx`, in the selection panel of the player's own complete training buildings): a button per trainable unit (cost via `CostList`, time; disabled when the queue is full or the stock is short), the queue as buttons that cancel, and a progress bar under the first. It selects one primitive string (queue, progress in 40 steps, waiting for housing), so it re-renders at most 40 times per unit.
- **Skeletons** (`CHARACTER_PACK.monsters`) are `SoldierModel`s too: the same baking and soldier instancing, no team cells, `Skeletons_*` clips from the Special library for idle, walk, taunt (minion `ready`) and death; their weapons (blade, axe, small shield, crossbow) are KayKit Skeletons accessories packed to GLB.
- **Dev spawn** (`ui/dev/DevSpawnPanel.tsx`, mounted only when `import.meta.env.DEV`, so production builds leave it out): sends `debugSpawn` at the camera focus (`render/camera/cameraFocus.ts`, a module value written by `RtsCameraControls`); the client store creates its `SimContext` with `{ dev: import.meta.env.DEV }`.
- **Professions** (`PROFESSIONS` in game-data) are cosmetic: a production building names its worker's profession, `UnitFrameDriver` resolves it from the worker's building, and the renderer gives the worker that hat and tunic color.
  - The walk clip's playback rate comes from its measured stride, so the feet don't slide. The clips are played in place; while a foot is planted (the lowest 8% of its height range), it moves backwards as fast as the body would move over the ground. That speed, measured at 120 fps over both feet, times the clip duration is the stride per cycle, and the rate is `speed · duration / stride`.
  - Unit picking (`screenPick`) and the placeholder serfs take their size from `CHARACTER_PACK.serf` (`height` · `scale`).
  - While the files load (Suspense), and if they fail (an error boundary), `PlaceholderUnits` draws the primitive serfs with procedural animation.
  - Rig compatibility was checked at import: all six Adventurers characters share the 23 Rig_Medium bones and rest pose of the Character Animations pack, so every clip plays on every character.
- **Construction sites.** `World` sends complete buildings to the instanced `Settlement` and sites to `ConstructionSites`. Each site draws a dirt plate, its look and a camera-facing progress bar (`SiteFrame`). Buildings (`construction: 'stages'`, the default) show the Hexagon pack's stages A–C (`HEXAGON_PACK.construction`), one at a time by thirds of the progress, all at one uniform scale fitted to 90% of the footprint; the scaffolding yard (scaled to the footprint) appears from stage B, and a flag at the front corner takes the owner's color through `singleTeamMaterial` (the uniform-color sibling of the instanced team material). Fields (`construction: 'reveal'`) show the real model with cloned materials and one clipping plane (`renderer.localClippingEnabled`, double-sided so the cut shows the inside of the walls). The placement ghost uses `singleTeamMaterial` too: each model material is cloned translucent, with the roof in the local player's color and a shared tint uniform (green / red, 25%) that validation switches. In `useFrame` it reads the site's progress from the store, interpolated between ticks, and moves the clip plane and the bar; there is no React re-render per tick. When a site finishes, the `buildings` array changes once and the building moves into the instancing.
- **Mouse scheme.** Left button: click selects a unit or building (Shift toggles units), drag box-selects own units (Shift adds). Right button: a click without movement commands the selected units (on an own construction site `assignBuilders`, anywhere else `moveUnits` to the ground point); a drag rotates the camera. Middle drag, WASD/arrows and, when enabled in the settings, the screen edges (10 px band, paused while a button is held) pan the camera, so a trackpad without a middle button works. Esc clears the selection; while the construction tool is active, its own input owns every press.
- **Pointer target, cursors and command feedback.** `pickPointerTarget` (in `input/`) picks every layer under a screen point with one ray: an own unit (screen space), the first building box, and the ground point with its walkability (nav grid), its reachable destination (`nearestWalkablePoint` from `@roe/sim`, the same goal rule as `findPath`) and the tree or rock there. Click-select, the right-click command (`commandIntent`) and the hover cursor (`cursorFor`) all read it, so the cursor always shows what a click would do. `useHoverCursor` re-picks at most once per frame and only when the pointer, camera matrix, game state, selection or tool changed, and writes the canvas `data-cursor` attribute only when the kind changes. `ui/cursors/cursors.css` maps kinds to original SVG cursors (drawn on a 32-unit grid, exported at 64 px, shown via `image-set(... 2x)`). Right-clicking water or a steep slope moves the units to the nearest walkable spot (the marker shows that spot). Right-clicking another building or a point with nothing reachable sends nothing; the sim would accept some of these moves, so this is a client-side choice. A harvestable tree or rock shows the axe or pickaxe (`RESOURCE_CURSOR`) and sends `gather`; non-harvestable ones (the border forest) are blocked. Accepted commands push an event to `commandFeedback`; `CommandMarkers` drains it in `useFrame` into fixed pools: a 16-slot instanced ground quad with a procedural shader (move: chevrons converging and a closing ring, tilted to the terrain; site: an outline shrinking onto the footprint and pulsing) and four hammer sprites (the cursor SVG rasterized at 256 px) above the site. Nothing re-renders React.
- **Selection.** `useSelectionInput` decides what a press means. Units are picked in screen space (`screenPick`): their interpolated positions are projected with the camera and compared in pixels. That is cheap for hundreds of units and independent of the instanced meshes. Buildings are picked with a ray against each oriented footprint box with a rough height (`pickBuilding`). `Units` publishes the positions it drew each frame in `renderedUnits`, which `SelectionRings` (one instanced mesh, mounted after `Units`) and picking read. The box rectangle is a DOM element moved directly (`dragBox`), not React state. `selectionStore` holds the ids. The HTML `SelectionPanel` shows the selected serfs (working, walking, idle) or the selected building; at the player's own Town Hall it offers "Recruit serf" with the serf count.
- **Deposits.** `checkPlacement` adds the `deposit` issue for buildings whose `process` production names a `deposit` (mines) when their center isn't within a deposit of that ore (`depositAt`); the menu turns it into "Must be built on a gold / an iron deposit". `Deposits` (client) draws each deposit as a terrain-following patch with vertex alpha (tinted center, transparent edge) and five veined low-poly rocks per ore kind (instanced), hidden once a building covers the deposit's center. The construction menu is a grid: one row up to seven buildings, otherwise two balanced rows, so it stays clear of the side panels.
- **Placing buildings.** The construction menu (HTML) picks a buildable type. `PlacementPreview` casts the mouse ray against the shared height field, snaps to the 1-unit grid, and colors a ghost green or red using the same `checkPlacement` the server runs (re-checked only when the cell, rotation or state changes). A click without movement places the building, Shift keeps the tool active, R rotates by 90°, and Esc or a right click cancels. Camera drags still work, because only near-motionless presses count as clicks.
- **Incremental updates after a placement.** Only terrain vertices within 7 units of the new footprint are re-sampled; normals and colors are recomputed only for those vertices and their direct neighbours (same area-weighted normals as a full pass, using a cached vertex-to-triangle map), and only the changed buffer ranges are uploaded. Trees, grass and props keep their generated heights outside the changed areas (`GroundLevel`), and only chunks touching those areas are rebuilt, so unchanged instance buffers aren't re-uploaded. Grass and props under the new building are removed.
- **The sun follows the camera.** The directional light and its target track the camera focus point. The shadow frustum scales with zoom in steps of 10 units, and its position is snapped to whole shadow-map texels so shadow edges don't shimmer while panning.

### `@roe/server`: the authoritative server

A Colyseus server. It uses only `@colyseus/core`, `@colyseus/ws-transport` and `@colyseus/schema`, not the `colyseus` meta-package, which would pull in Redis, the monitor and other extras. `MatchRoom` is a placeholder 2–4 player room whose synchronized `MatchState` holds the map id and the player list.

The room runs `stepGame` at `SIMULATION_TICK_RATE` via `setSimulationInterval`. It accepts `command` messages: it parses the payload with `parseCommand`, takes the issuer from `client.sessionId` (never from the message), queues the command for the next tick, and replies with `commandResult` once the tick has applied it. Its starting settlement is neutral for now, so nobody can recruit there yet. Syncing the state to clients comes with the multiplayer phase.

## Multiplayer model (planned)

```text
client input ──► command ──► server validates (shared rules) ──► applies to state
                                                                       │
client renders ◄──────────── state patches (Colyseus schema) ◄─────────┘
```

- Clients send **commands** ("build X at Y", "move units to Z") and never send state.
- The server checks every command against `@roe/shared` rules: resources, placement, ownership and cooldowns.
- The simulation runs at a fixed tick (`SIMULATION_TICK_RATE`).
- The client may predict locally using the same shared rules, then reconcile with the server state.
- Procedural content such as map decorations is generated from seeds, so it never has to be sent over the network.

PostgreSQL will store persistent player data (accounts, profiles, match history). Live match state stays in memory in the room.

## Workspace package resolution

Workspace packages are consumed **directly from their TypeScript sources** during development and type checking. A custom export condition makes this possible:

```jsonc
// packages/shared/package.json
"exports": {
  ".": {
    "@roe/source": "./src/index.ts",   // dev / typecheck
    "types": "./dist/index.d.ts",      // compiled consumers
    "default": "./dist/index.js"
  }
}
```

| Consumer                | How it enables `@roe/source`                         |
| ----------------------- | ---------------------------------------------------- |
| TypeScript (`tsc`, IDE) | `customConditions` in `tsconfig.base.json`           |
| Vite (client)           | `resolve.conditions` in `apps/client/vite.config.ts` |
| tsx (server dev)        | `--conditions=@roe/source` in the `dev` script       |
| Node (server prod)      | not enabled, so it uses the compiled `dist/`         |

Each package's `tsconfig.build.json` clears `customConditions`, so production builds compile against the other packages' `dist/` output. `pnpm build` (`pnpm -r build`) builds packages in dependency order.

What this gives you: hot reload across packages, go-to-definition that lands in source, and no build step before `pnpm dev`.

## Adding a new package

1. Create `packages/<name>/` with `package.json` (name `@roe/<name>`, the `exports` map above, and `build`, `typecheck` and `clean` scripts).
2. Copy `tsconfig.json` and `tsconfig.build.json` from `packages/shared`.
3. Add it as a dependency with `"@roe/<name>": "workspace:*"` and run `pnpm install`.

## Code conventions

- Strict TypeScript, including `noUncheckedIndexedAccess`, with `verbatimModuleSyntax` (always `import type` for types).
- Relative imports in `shared`, `game-data` and `server` use the `.js` extension (NodeNext resolution). The client uses bundler resolution without extensions.
- One React component per file, named after the component.
- Formatting is handled by Prettier only; ESLint does not check style.
